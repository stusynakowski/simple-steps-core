# What we are building

> Design status: **proposed, 2026-10-26**, on branch `core-handover`. Nothing
> here is built yet unless it says *exists today*. These documents come before
> the code changes and are the contract the code is changed to meet. The
> inputs they were drawn from are in [`core-handover/`](../../core-handover/)
> (generated by the Simple Steps repo, kept read-only).

## The purpose

`simple-steps-core` is the **engine** of Simple Steps. Simple Steps is a web
application (separate repo, `Simple_Steps`) where many users build, run and
inspect workflows through an interactive UI and an agent. Core is the part of
that application that knows what a workflow *is* and how it runs. Everything
else is the app's.

The test of the boundary:

> **Everything Simple Steps can do to a workflow can be done to a `Kernel` in
> a plain Python session** (a terminal, IPython or a Jupyter notebook), with
> only core installed: declare steps, run them, read values, states and
> problems, save and load.

If the app works out a fact about a workflow (why a step is stale, what a cell
came from, whether a formula is valid against the tools), that fact belongs in
core, and the app reads it.

## Core and the app

| Core (this repo) | The app (`Simple_Steps`) |
|---|---|
| The object model: catalog, tools, modifiers, resources, references, operations, steps, outputs, workflows, kernels | Hosting many kernels: keys, locks, last-used, eviction |
| Declaring a step and saying what is wrong with it (structured problems) | The formula bar's text parser: text → `Operation` |
| Running steps, cell states, staleness, versions | Users, sessions, HTTP routes, the workspace and its files |
| Specs: saving and loading a kernel's recipe | Where specs and output snapshots are stored |
| A readable terminal view of a kernel, a step, a cell | Cell views (PNG, Plotly), the UI, paging in the browser |
| Room for the app's own data on every spec (`extras`) | What goes in `extras`: UI widgets, agent permissions |
| — | The agent and its conversation |

Core never imports the app, never knows about HTTP, users or UI, and keeps no
mutable state at module level, so one Python process can hold many kernels
that cannot see each other.

## Rules for working on core

These carry over from the app's handover and apply to every change:

1. **One model.** The grid model is the only model. Anything else is moved
   onto it or removed.
2. **Verify by running.** A claim about behaviour is checked by running core,
   never by reading docs (including these).
3. **No mutable state at module level.** Everything a workflow uses hangs off
   its kernel.
4. **An empty step** is a 1×1 frame with one cell `"empty"`, never a
   placeholder.
5. **Extras live under a namespace and are never hashed.**
6. **Behaviour changes land in small, confirmed pieces.** A restructure that
   changes no behaviour keeps the existing tests green. A change in behaviour
   is confirmed by the owner before it lands.
7. **One word, one meaning,** as defined in
   [object-model.md §1](object-model.md#1-the-words). New code uses those
   words; a name that drifts from them is a bug.
